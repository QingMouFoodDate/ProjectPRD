# 《轻眸识刻》工程协作与规范指南

> **规范性质**：全系统开发流转、文档排版、代码协同与 Git 提交硬性标准  
> **适用范围**：`QingMouFoodDate` 组织下全部 6 个代码仓库及协同工作区

---

## 一、 文档编写与排版原则

1. **客观严谨，专业克制**：
   - 描述功能场景、接口出入参及验收标准，杜绝公文式套话与营销化浮夸措辞；
   - 正式技术文档中严禁使用装饰性表情符号（emoji）；
   - 数学公式与符号使用纯文本表达（例如映射用 `->`，乘除用 `*`、`/`，范围用 `>=`）。
2. **标题无括号铁律**：
   - 所有 Markdown 各级标题（`#`、`##`、`###`、`####`）末尾**严禁出现任何中英文括号及其附注内容**。
3. **目录结构展示粒度**：
   - 目录树状图仅展示根目录核心文件与模块文件夹层级，避免展开底层具体代码文件；
   - 树状图中的每一行均需附带简短对齐的中文注释，说明该文件或目录的具体功能与职责定位。
4. **隐私与环境解耦**：
   - 严禁在代码仓库文档中出现任何本地专属私有路径（如本地离线 reports、data 等文件夹字样）。
5. **判定对象伦理底线**：
   - 涉及保质期状态，判定对象严格限定为“包装标示状态”，严禁直接输出“绝对安全可食用”等主观断言。

## 二、 Git 分支管理与提交规范

### 1. 分支管理模型
团队采用轻量稳定的主干开发与特性分支协同模式：
- **`main` 主干分支**：保证始终处于随时可构建、可运行状态，受保护，禁止直接强制推送（force push）；
- **`feat/*` 特性分支**：从 `main` 拉出，完成具体独立切片后通过 PR 或测试核验合并入 `main`；
- **`fix/*` 修复分支**：针对联调或运行中暴露的缺陷进行针对性热修复。

### 2. 提交信息格式规范
代码提交说明统一遵循 Conventional Commits 格式：`<emoji> <type>: <简明中文改动>`（或 `<emoji> <type>(<作用域>): <简明中文改动>`）：

| 提交前缀 | 语义说明 | 适用场景示例 |
| :--- | :--- | :--- |
| `🎉 init` | **项目初始化** | 仓库初始工程结构搭建、基础配置文件创建 |
| `✨ feat` | **添加新特性** | 新增会话接口、新增 Canvas 绘制组件、新增数据增强算子 |
| `🐞 fix` | **修复缺陷** | 修复日期解析闰年错误、修复跨域异常、修复移动端旋转角误差 |
| `🎈 perf` | **性能与体验优化** | 优化模型推理耗时、提升前端缩略图加载流畅度 |
| `🦄 refactor` | **代码重构** | 调整代码分层解耦、重命名变量，不影响原有逻辑功能 |
| `📃 docs` | **修改文档** | 补充或更新 README、API 接口协议、系统架构图、注释说明 |
| `🌈 style` | **格式缩进调整** | 代码排版、分号、空格调整，不影响实际运行逻辑 |
| `🧪 test` | **测试用例** | 增加单元测试、集成测试用例、自动化质检测试 |
| `🔧 build` | **依赖相关** | `requirements.txt`、`package.json`、构建脚本或打包配置调整 |
| `🐎 ci` | **CI/CD 配置** | GitHub Actions 持续集成脚本、自动化部署流水线微调 |
| `🐳 chore` | **构建或辅助工具** | 辅助脚本、开发期抓取工具、环境辅助配置变更 |
| `↩ revert` | **版本回滚** | 回滚撤销此前某次错误的提交 |

### 3. 提交前真实核验网关
在本地工作区执行提交前，必须严格完成核验：
1. **Git 状态核实**：提交前先运行 `git status` 与 `git diff`，确认改动范围准确，无多余的本地临时文件（如 `.pyc`、`node_modules`、`.DS_Store`、日志）；
2. **真实检查与测试运行**：运行项目已有且与改动相关的测试命令，仅对实际在终端中执行过且通过的测试声称通过；
3. **大文件物理隔离红线**：严禁将高容量原图集、视频切片、训练权重权重包（`*.pth`、`*.onnx`）直接 commit 进代码仓历史。

## 三、 团队工程协作原则

1. **契约先行，接口解耦**：各仓库间以 `contracts/` 目录下的统一协议为唯一协同准则，内部实现细节互不耦合；
2. **聚焦轻量闭环，优先单机验证**：立足大创实际，优先在单机环境跑通“传图 ➔ 识别 ➔ 圈框展示 ➔ 算标示期”的最小可用闭环（MVP），拒绝过度分布式设计；
3. **任务导向协作机制**：团队内部按技术任务方向模块化推进，开工前先对齐契约，完成后以功能要求与验收标准自测；
4. **先核验、后执行、再复检**：凡涉及数据入库、目录变更、接口变更或配置调整，执行前必须读取确认前置状态，执行后必须实测校验结果。
