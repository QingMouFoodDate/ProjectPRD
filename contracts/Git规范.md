# 《轻眸识刻》多仓库 Git 分支管理与提交规范

> **规范性质**：全域 6 大仓库开发流转与代码协同硬性标准  
> **适用范围**：`ProjectPRD`、`TrainPlatform`、`ModelTrain`、`WebClient`、`MobileClient`、`WxClient`

---

## 一、 分支管理模型

团队采用轻量稳定的主干开发与特性分支协同模式：

```text
main (长期稳定主干，受保护，禁止直接 force push)
 │
 ├── feat/web-session-ui      (功能特性分支，开发完成后通过 PR / 校验合并)
 ├── feat/model-p2-head       (算法演进分支)
 └── fix/cors-gateway         (缺陷修复分支)
```

1. **`main` 主干分支**：
   - 保证始终处于随时可运行状态；
   - 需通过自动化门禁或团队成员交叉验证后方可合并。
2. **`feat/*` 特性分支**：
   - 从 `main` 拉出，完成具体独立切片后向 `main` 发起合并。
3. **`fix/*` 修复分支**：
   - 针对线上或联调中暴露的缺陷进行针对性修复。

## 二、 提交信息规范

代码提交说明遵循统一的语义化格式：`<emoji> <type>: <简明中文改动>`（或 `<emoji> <type>(<作用域>): <简明中文改动>`）：

| 提交前缀 | 语义说明 | 适用场景示例 |
| :--- | :--- | :--- |
| `🎉 init` | **项目初始化** | 仓库初始工程结构搭建、基础配置文件创建 |
| `✨ feat` | **添加新特性** | 新增会话接口、新增 Canvas 绘制组件、新增数据增强算子 |
| `🐞 fix` | **修复缺陷** | 修复日期解析闰年错误、修复跨域异常、修复移动端旋转角误差 |
| `🎈 perf` | **性能与体验优化** | 优化模型推理耗时、提升前端缩略图加载流畅度 |
| `🦄 refactor` | **代码重构** | 调整代码分层解耦、重命名变量，不影响原有逻辑功能 |
| `📃 docs` | **修改文档** | 补充或更新 README、API 接口协议、系统架构图、注释说明 |
| `🌈 style` | **格式缩进调整** | 代码排版、分号、空格调整，不影响实际运行逻辑 |
| `🧪 test` | **测试用例** | 增加单元测试、集成测试用例、自动化质检测试 |
| `🔧 build` | **依赖相关** | `requirements.txt`、`package.json`、构建脚本或打包配置调整 |
| `🐎 ci` | **CI/CD 配置** | GitHub Actions 持续集成脚本、自动化部署流水线微调 |
| `🐳 chore` | **构建或辅助工具** | 辅助脚本、开发期抓取工具、环境辅助配置变更 |
| `↩ revert` | **版本回滚** | 回滚撤销此前某次错误的提交 |

## 三、 提交前核验规范

在本地工作区执行提交前，必须严格完成核验：

1. **Git 状态核实**：
   - 提交前先运行 `git status` 与 `git diff`，确认改动范围准确，无多余的本地临时文件（如 `.pyc`、`node_modules`、`.DS_Store`、日志）；
2. **真实检查与测试运行**：
   - 运行项目已有且与改动相关的静态检查或测试命令；
   - 仅对实际在终端中执行过且通过的测试声称通过，无法运行或存在告警时如实记录；
3. **大型二进制文件物理隔离红线**：
   - 严禁将大容量图片数据集、深度学习权重文件（`*.pth`、`*.onnx`）直接提交进代码仓库；
   - 图像数据集存放在集中样本存储服务中，申报与汇报材料归档至本地独立离线目录，严禁提交进 Git 代码历史。
