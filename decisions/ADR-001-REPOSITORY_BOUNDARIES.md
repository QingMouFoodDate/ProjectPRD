# ADR-001 八仓职责与在线离线边界

- **状态**：Accepted，仅指仓库职责设计决议。
- **日期**：2026-10-05。
- **批准依据**：用户已批准推荐方案；本文记录该授权，不列未经确认的成员实名。
- **适用范围**：现有八仓的目标职责及分阶段迁移。
- **实现状态**：M0 待实现；生产契约、字段、接口、模型形状及具体功能仍为候选或待实现。

## 一、背景

旧文档存在仓库数量不一致、在线模型执行与离线治理混用、ModelTrain 导出后直达线上、业务纠偏与训练接纳绑定等表述。本决议明确治理、执行与在线决策职责，避免为逻辑模块新增仓库或扩大首个原型范围。

## 二、决议

### 1. 保留八仓与原名

| 仓库 | 目标职责 |
| :--- | :--- |
| `.github` | 组织公共说明与协作入口，不承担业务实现 |
| `ProjectPRD` | 需求、架构、设计决议、候选契约与质量规范 |
| `TrainPlatform` | 离线样本、数据集、标注审核、训练调度、评测登记、模型注册及发布治理 |
| `ModelTrain` | 训练、评测、模型导出执行，只读已审核冻结数据 |
| `InferPlatform` | 在线业务 API、会话、资产、编排、Evidence、日期 Decision 与业务纠偏；包含内部 runtime |
| `WebClient` | 在线识别、展示、证据查看和纠偏交互，优先 M0 单图原型 |
| `MobileClient` | 候选移动增强客户端，暂停实现，保留仓库 |
| `WxClient` | 候选微信入口，暂停实现，保留仓库 |

MobileClient 与 WxClient 暂停实现不是合并或删除。八仓不重命名；与本决议冲突的旧职责说明弃用。职责描述为目标设计，不代表已有对应功能。

不新增 Data、Registry、Gateway、Runtime 仓。离线数据与模型注册属于 TrainPlatform 模块，业务接入与 runtime 属于 InferPlatform 模块；模块独立不等于仓库、服务或部署节点必须独立。

### 2. 分离治理与执行

- TrainPlatform 负责来源许可管理、数据审核、标注审核、`group_key` 切分、冻结版本、训练任务调度和评测登记。
- ModelTrain 接收冻结版本与任务配置，只读执行训练、评测和导出，不修改原图、标签或切分，不自行批准训练资格或线上发布。
- 模型 `register / validate / release` 归 TrainPlatform 治理；ModelTrain 提供模型包和评测产物作为依据。
- 模型 `activate / rollback` 归 InferPlatform 控制，内部 runtime 校验并执行；release 仅授予交付资格，不自动替换线上模型。
- runtime 负责模型加载、预处理、检测和 OCR，仅产出 Observation；不负责会话、证据聚合、日期规则、业务状态或食品安全结论。

### 3. 分离业务纠偏与训练资格

InferPlatform 接受业务纠偏后保存原始 Observation、人工修正及版本，立即重算 Evidence/Decision，不等待训练审核。TrainPlatform 对获授权的回流独立审核来源许可、标注质量、防泄漏条件与训练资格；未审或拒绝记录不能进入冻结训练集，人工修正不自动成为训练真值，不自动触发训练或更新模型。

### 4. 明确阶段与状态

- M0 为 Planned 的 C0 单图切片，待实现：单图上传、检测/OCR、Observation -> Evidence -> Decision 与基础 Web 展示。
- M0 不包含多图、完整纠偏审核、MobileClient、WxClient、端侧推理或 TrainPlatform 完整实现。
- C0 核心目标保留多图会话、全景画布、双维度状态卡片与纠偏审核回流；C1 为增强、C2 为实验、C3 为储备。
- 无验收链接的需求标为 Planned/Proposed。性能与准确率目标无数据时标为未测量，示例不是实测。
- P2 检测头与受限 OCR 仅为候选研究方案，不因本决议成为生产算法选型。

## 三、候选契约与质量要求

人工契约分为 API、DATA、DATE_RULES、MODEL、TRAINING。候选机器契约已纳入本仓：`contracts/openapi.json` 及 `contracts/schemas/` 下四份 Schema。这些文件仍为候选，结构校验通过不表示生产冻结。

数据质量覆盖来源许可、bbox/OCR/语义标注、分组切分防泄漏、审核冻结及 negative/hardcase 隔离。SHA-256 用于完整性查重，pHash 用于近重复线索，二者均非真实性证明。禁止伪造标签和拼图粗审。

会话和业务资产由 InferPlatform 管控，离线样本与模型治理资产由 TrainPlatform 管控，训练与公开使用许可分别审核。

## 四、迁移顺序

1. **文档**：统一需求、架构、质量与工程规则；契约评审版本化，未完成前保持候选状态。
2. **代码**：在各实现仓按契约版本迁移职责，保留原仓名，优先实现 M0。
3. **测试**：补充契约一致性、只读冻结输入、重算与审核隔离、版本切换测试，提供验收记录。
4. **CI**：将能实际运行的检查纳入门禁；文档仓校验文档和契约，不宣称产品运行验证。

后续实施由对应仓库在明确授权与实际验证后推进。

## 五、影响与风险

- 保留八仓可避免结构性迁移，但需持续检查 README、契约和实现的职责一致性。
- 治理与执行分离增加冻结版本、登记和审计要求，M0 先满足最小人工审核前置。
- 旧契约若有历史措辞或示例数值需后续修订，不能直接据此认定达标。
- 单图 M0 降低首轮交付复杂度，但非完整 C0，后续多图与纠偏审核须分别验收。
