# ADR-001 八仓职责与在线离线边界

- **状态**：Accepted，仅指仓库职责设计决议。
- **日期**：2026-10-05。
- **批准依据**：用户已批准终检推荐方案；本文记录该授权，不冒充团队会签，不列未经确认的成员实名或签字。
- **适用范围**：现有八仓的目标职责及分阶段迁移。
- **实现状态**：M0 待实现；生产契约、字段、接口、模型形状及具体功能仍是候选或待实现。

## 一、背景

旧文档存在仓库数量不一致、在线模型执行与离线治理混用、ModelTrain 导出后直达线上、业务纠偏与训练接纳绑定等表述。需要明确治理、执行与在线决策的责任，同时避免为逻辑模块新增仓库或扩大首个原型范围。

## 二、决议

### 1. 保留八仓与原名

| 仓库 | 目标职责 |
| :--- | :--- |
| `.github` | 组织公共说明与协作入口，不承担业务实现 |
| `ProjectPRD` | 需求、架构、设计决议、候选契约与质量规范 |
| `TrainPlatform` | 离线样本、数据集、标注审核、训练调度、评测登记、模型注册及发布治理 |
| `ModelTrain` | 训练、评测、模型导出执行，只读已审核冻结数据 |
| `InferPlatform` | 在线业务 API、会话、资产、编排、Evidence、日期 Decision 与业务纠偏；包含内部 runtime |
| `WebClient` | 在线识别、展示、证据查看和纠偏交互，优先 M0 单图原型 |
| `MobileClient` | 候选移动增强客户端，暂停实现，保留仓库 |
| `WxClient` | 候选微信入口，暂停实现，保留仓库 |

MobileClient 与 WxClient 暂停实现不是强制合并或删除。八仓不重命名；与本决议冲突的旧职责说明弃用，但不自动删除旧文档或改写历史。职责描述是目标设计，不代表这些仓库已有对应功能。

不新增 Data、Registry、Gateway、Runtime 仓。离线数据与模型注册分别属于 TrainPlatform 模块，业务接入与 runtime 属于 InferPlatform 模块；模块独立不等于仓库、服务或部署节点必须独立。

### 2. 分离治理与执行

- TrainPlatform 拥有来源许可管理、数据审核、标注审核、`group_key` 切分、冻结版本、训练任务调度和评测登记。
- ModelTrain 接收冻结版本与任务配置，只读执行训练、评测和导出，不修改原图、标签或切分，不自行批准训练资格或线上发布。
- 模型 `register / validate / release` 归 TrainPlatform 治理；ModelTrain 提供模型包和评测产物作为依据。
- 模型 `activate / rollback` 归 InferPlatform 控制，内部 runtime 校验并执行；release 只授予交付资格，不自动替换线上模型。
- runtime 负责模型加载、预处理、检测和 OCR，仅产出 Observation；不负责会话、多图证据聚合、日期规则、业务状态或食品安全结论。

### 3. 分离业务纠偏与训练资格

InferPlatform 接受业务纠偏后保存原始 Observation、人工修正及版本，立即重算 Evidence/Decision，不等待训练审核。TrainPlatform 对获授权的回流独立审核来源许可、标注质量、防泄漏条件与训练资格；待审或拒绝记录不能进入冻结训练集，人工修正不自动成为训练真值，不自动触发训练或更新模型。

### 4. 明确阶段与状态

- M0 为 `Planned` 的 C0 单图切片，待实现：单图上传、检测/OCR、Observation -> Evidence -> Decision 与基础 Web 展示。
- M0 不包含多图、完整展示和纠偏审核、MobileClient、WxClient、端侧推理或 TrainPlatform 完整实现。
- C0 核心最终目标保留多图会话、全景画布、微距视窗、二维状态卡片、手动补录和纠偏审核回流；C1 为增强、C2 为实验、C3 为储备。
- 无验收链接的需求仅使用 Planned/Proposed。设计采纳不提升功能实现状态；性能、准确率目标无数据时标为未测量，示例不是实测。
- P2 检测头与受限 OCR 仅为候选研究方案，不因本决议成为生产算法选型。

## 三、候选契约与质量要求

人工契约分为 API、DATA、DATE_RULES、MODEL、TRAINING。候选机器契约已经纳入本仓：`contracts/openapi.json` 及 `contracts/schemas/observation.v1.schema.json`、`contracts/schemas/evidence.v1.schema.json`、`contracts/schemas/decision.v1.schema.json`、`contracts/schemas/correction.v1.schema.json`。这些文件仍为候选；文件存在或结构校验通过不表示生产冻结、功能实现或真实模型验证完成。

数据质量必须覆盖来源与许可、bbox/OCR/语义标注、分组切分防泄漏、审核冻结及 negative/hardcase 隔离。SHA-256 用于完整性与精确查重，pHash 用于近重复线索，二者均不是真实性证明。禁止伪造标签和拼图粗审的规则继续适用。

公开文档不授予资产访问权；实际仓库可见性、成员权限与分支保护以平台配置为准。会话和业务资产由 InferPlatform 管控，离线样本与模型治理资产由 TrainPlatform 管控，训练和公开使用许可分别审核。

## 四、迁移顺序

1. **文档**：统一需求、架构、质量与工程规则；契约在独立授权工作中补齐、评审并版本化，未完成前保持候选状态。
2. **代码**：在各实现仓按明确的契约版本逐项迁移职责，保留原仓名与可追溯映射，先实现 M0。
3. **测试**：补充契约一致性、只读冻结输入、业务重算与训练审核隔离、模型治理与版本切换测试，提供验收链接。
4. **CI**：将已能实际运行的检查纳入各仓门禁；文档仓校验文档和契约，不宣称提供产品运行验证。

不自动重写提交历史；本决议不授权清理他人改动、解决其他仓的合并状态、提交或推送。后续实施须由对应仓库在明确授权与实际验证后推进。

## 五、影响与风险

- 保留八仓可避免结构性迁移，但需要持续检查 README、契约和实现的职责一致性。
- 治理与执行分离增加显式的冻结版本、登记和审计要求，M0 可先满足最小人工审核前置，不要求完整平台。
- 旧契约可能仍有强制措辞、字段不一致或示例数值，需后续修订；不能直接据此生成生产实现或认定达标。
- 单图 M0 降低首轮交付复杂度，但不是完整 C0，后续多图与纠偏审核必须分别验收。
